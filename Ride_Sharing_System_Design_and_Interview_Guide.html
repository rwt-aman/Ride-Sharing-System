🚗 Ride Sharing System — FAANG System Design & Interview Guide

Complete High-Level Design (HLD), Low-Level Design (LLD), Security Architecture & 20 FAANG Interview Q&A
Frontend: Netlify CDN (HTML/CSS/JS) Backend: Render (Express.js/Node.js) Database: MongoDB Atlas Cloud Security: Bcrypt + Institutional Domain Auth

🏛️ 1. High-Level Design (HLD) Architecture

The system is built on a decoupled, cloud-native 3-tier client-server architecture designed for high availability, low latency, and ease of horizontal scaling.

System Architecture Hierarchy:
  • Presentation Tier (Netlify Edge CDN): Globally distributed edge nodes delivering index.html, style.css, and app.js with sub-50ms TTFB.
  • Application Tier (Render Compute Service): Stateless Node.js / Express.js server exposing 14 RESTful JSON endpoints, handling CORS preflight, payload validation, and Bcrypt hashing.
  • Data Persistence Tier (MongoDB Atlas Cloud): Managed MongoDB replica cluster maintaining ACID document transactions across Users, Rides, and Bookings.
Key HLD Trade-off: Decoupled SPA vs Server-Side Rendering (SSR)

Decision: Decoupled Single-Page Architecture deployed across separate origins (Netlify + Render).
Pros: Zero server compute for serving static assets, independent CI/CD pipelines, global CDN edge caching.
Cons: Requires CORS cross-origin configuration and handling preflight OPTIONS requests.

🔄 2. End-to-End Data Flow & Business Logic

A. Identity & Authentication Pipeline:

  1. Registration: Client sends { studentId, fullName, phoneNumber, email, password } → Server verifies institutional domain suffix (@gehu.ac.in) → Hashes password with Bcrypt (10 salt rounds = 1024 iterations) → Writes to MongoDB Users collection.
  2. Login: Client sends email + password → Server retrieves user record → Runs constant-time bcrypt.compare() → Returns sanitized user metadata (excluding password hash) to client memory.

B. Ride Posting & Lifecycle Pipeline:

  1. Posting: Rider specifies origin gate, destination, departure date/time, seat count, and notes → Saved to Rides collection.
  2. Modification & Cascade Deletion: Updating or deleting a ride verifies ownership via studentId. Deleting a ride initiates cascade deletion of all associated child records in Bookings to prevent orphan state.

C. Booking State Machine & Atomic Seat Accounting:

  1. Booking Request: Seater requests ride → Record created in Bookings with status: 'pending'. Duplicate guard query ensures no concurrent un-rejected booking exists.
  2. Acceptance & Atomic Decrement: Rider approves → Status changes to accepted → Available seats decrement atomically via MongoDB $inc: { seatsAvailable: -1 } to prevent race conditions.
  3. Cancellation & Conditional Restoration: Seater cancels → Server checks if booking was accepted; if yes, restores seat via $inc: { seatsAvailable: 1 } before deleting booking record.

🗄️ 3. Database Schema (Low-Level Design / LLD)

Collection Key Attributes Indexes / Constraints Design Rationale
Users studentId (PK), fullName, phoneNumber, email, password, timestamps Unique index on studentId and email String-based studentId enables fast logical foreign-key checks without join latency.
Rides _id (PK), studentId (FK), riderName, phone, source, destination, rideDate, timeToLeave, seatsAvailable, note Index on rideDate + destination Atomic integer seatsAvailable supports non-blocking concurrent seat allocations.
Bookings _id (PK), rideId (ObjectId FK ref), seaterStudentId, seaterName, seaterPhone, destination, rideDate, rideTime, status, bookingTime rideId ref to Ride; status enum [pending, accepted, rejected] Supports Mongoose populate("rideId") for eager-loading full ride context.

🔐 4. Security & Cryptographic Architecture

  • Adaptive Hashing (Bcrypt): 10 salt rounds (210 = 1024 iterations) with cryptographically secure pseudo-random salt generator (CSPRNG) prevents rainbow table and GPU brute-force attacks.
  • User Enumeration Defense: Unified error message ("Invalid email or password") for both invalid emails and wrong passwords prevents username discovery.
  • Concurrency Protection: Atomic updates via MongoDB $inc prevent double-booking race conditions during high-volume requests.

🎤 5. Top 20 FAANG Interview Questions & Model Answers

Q1: Can you walk me through the end-to-end architecture of your system?
"The application is architected as a decoupled client-server web app. The presentation tier is a lightweight vanilla SPA hosted on Netlify CDN for edge-cached low latency. The backend is an Express.js Node runtime on Render exposing 14 RESTful endpoints. The persistence tier is MongoDB Atlas. The client communicates via asynchronous fetch() over HTTPS with JSON serialization. Cross-Origin Resource Sharing (CORS) is enabled to allow multi-origin communication. Authentication is secured using Bcrypt with a work factor of 10."
Q2: How do you prevent race conditions when two users simultaneously book the last seat?
"In MongoDB, document updates using atomic operators like $inc are atomic at the document level. To fully guard against negative seat counts under concurrency, the acceptance logic leverages conditional optimistic concurrency: Ride.findOneAndUpdate({ _id: rideId, seatsAvailable: { $gt: 0 } }, { $inc: { seatsAvailable: -1 } }). If two riders accept concurrently on 1 remaining seat, only the first transaction finds a matching document with seatsAvailable > 0, while the second receives null and returns an out-of-capacity error."
Q3: Why choose NoSQL (MongoDB) over SQL (PostgreSQL/MySQL) for this use case?
"MongoDB provides flexible document modeling for rides and bookings, rapid horizontal sharding capabilities, and native JSON support with Mongoose ODM. In an interview, I also highlight the trade-offs: while MongoDB excels in schema agility and horizontal reads, a strict relational database with foreign key cascades and multi-table ACID transactions (like PostgreSQL) would offer native referential integrity enforcement without requiring manual application-level cascade deletions."
Q4: Explain your password hashing algorithm and why salt rounds matter.
"We use Bcrypt, an adaptive key-derivation function based on the Blowfish cipher. Salt rounds define the computational cost (2cost). At 10 rounds, it runs 1,024 iterations. The salt is generated with cryptographically secure pseudo-random numbers (CSPRNG) and prepended to the hash string. This renders pre-computed rainbow table attacks impossible. Because Bcrypt is intentionally CPU-intensive, it resists offline GPU brute-force attacks while remaining negligible (~80ms) for legitimate login requests."
Q5: How does your search query work and how would you optimize it at scale?
"Currently, /search-rides matches rideDate and uses case-insensitive regex on destination combined with seatsAvailable: { $gt: 0 }. At scale (millions of rides), regex scans are unindexed and slow. I would optimize this by: (1) creating a compound index on { rideDate: 1, destination: 'text', seatsAvailable: 1 }, (2) implementing geospatial indexing using MongoDB's 2dsphere index with $nearSphere coordinates for true proximity search, and (3) adding an in-memory Redis cache with a 30-second TTL for hot destination queries."
Q6: What happens during ride cancellation or rejection? Walk through the seat accounting.
"When a rider rejects a pending booking, only the booking status is changed to 'rejected'—no seat count modification is made because seats are only reserved upon acceptance. When a passenger cancels an existing booking, the server first inspects the status: const wasAccepted = booking.status === 'accepted'. The booking document is deleted, and only if wasAccepted === true does the backend execute $inc: { seatsAvailable: 1 } to restore inventory."
Q7: How do you prevent duplicate bookings from the same user on the same ride?
"Before creating a booking record, the backend runs a duplicate guard query: Booking.findOne({ rideId, seaterStudentId, status: { $ne: 'rejected' } }). If a record is found with status either pending or accepted, the request is rejected with a 400 status. However, if the previous booking was rejected, the query returns null, allowing the user to re-request if circumstances changed."
Q8: How did you implement cascade deletion when a rider deletes their ride?
"Because MongoDB does not enforce foreign key cascade deletes by default, the application layer coordinates the transaction: upon verifying ride ownership via Ride.findOne({ _id: rideId, studentId }), the backend executes Ride.findByIdAndDelete(rideId) followed immediately by Booking.deleteMany({ rideId }). This guarantees no orphaned booking records persist in the passenger view."
Q9: Explain the Mongoose populate() method used in your passenger dashboard.
"In /seater-bookings, bookings only store the foreign reference rideId. Using Booking.find({ seaterStudentId }).populate('rideId'), Mongoose executes a secondary batch query to the rides collection and replaces the raw ObjectId with the fully hydrated Ride document. This enables the client to display the rider's name, phone, departure time, and source gate in a single client payload."
Q10: What is the risk of your current authentication model and how would you fix it?
"Currently, user state is held in client memory (currentUser) and the studentId is passed in request payloads. This has two vulnerabilities: session loss on page reload and potential parameter tampering if an attacker sends another user's studentId. The production-grade fix is implementing stateless JSON Web Tokens (JWT) signed with HMAC-SHA256, transmitted via httpOnly, secure, SameSite=Strict cookies, verified by an Express authentication middleware on every private route."
Q11: How is theme switching (Dark/Light mode) implemented without CSS bloat?
"It uses a single CSS custom property token system declared in :root. Variables like --bg, --card, and --text are defined once. When toggled, JavaScript adds a .dark class to the root <body>, which overrides the variables under body.dark. The selection is synchronized to localStorage and evaluated on page load, achieving instantaneous rendering without layout recalculation or theme stylesheets."
Q12: How would you scale this application from 1,000 to 100,000 Daily Active Users (DAU)?
"1. Stateless Compute: Run multiple Express container instances behind an AWS Application Load Balancer (ALB) or Nginx reverse proxy.
2. Distributed Caching: Introduce Redis cluster for session storage and caching frequent ride routes.
3. Database Optimization: Implement MongoDB replica sets with Read Preference set to secondaryPreferred for search queries, reserving Primary node for writes.
4. Asynchronous Queues: Offload SMS/Email notifications to BullMQ / RabbitMQ message queues to keep HTTP response times under 50ms."
Q13: How would you add real-time tracking and instant ride matching?
"I would integrate WebSockets using Socket.io backed by a Redis Pub/Sub adapter. When a rider posts a ride or accepts a booking, events are pushed directly to subscribed client channels. For live vehicle tracking, client geolocation coordinates would be streamed at 5-second intervals via WebSockets, stored in Redis geospatial data structures (GEOADD / GEORADIUS) for instant proximity filtering."
Q14: Explain the difference between user authentication and authorization in this project.
"Authentication validates identity ('Who are you?') handled by the /login route using Bcrypt password comparison. Authorization validates permissions ('Are you allowed to do this?'), enforced on mutating routes like /edit-ride and /delete-ride by verifying that the modifying user's studentId matches the creator ID on the target ride document."
Q15: How do you handle CORS and what are the security risks of origin: "*"?
"CORS headers dictate which external origins can execute XMLHttpRequests. Setting origin: "*" allows any domain to hit the API. While functional for development, in production it allows Cross-Site Scripting (XSS) attackers on other domains to invoke endpoints. The secure production configuration restricts origin strictly to the trusted Netlify domain whitelist: origin: ['https://ride-sharing-system.netlify.app']."
Q16: How do you protect against NoSQL Injection attacks?
"NoSQL injection occurs when unvalidated user input contains MongoDB query operators like {"$gt": ""}. To prevent this: (1) employ strict schema validation via Mongoose which casts inputs to expected primitive types, (2) sanitize request payloads using libraries like express-mongo-sanitize which strip any keys beginning with $, and (3) enforce input validation schemas using Joi or Zod."
Q17: Why did you validate email addresses on both the frontend and backend?
"Defense in depth. Frontend validation (email.endsWith('@gehu.ac.in')) gives immediate UX feedback and prevents unnecessary network requests. Backend validation is non-negotiable because client-side checks can be trivially bypassed using Postman, curl, or direct HTTP scripts. The server is the authoritative gatekeeper for data integrity and institutional policy enforcement."
Q18: What is your API's error handling strategy?
"Every route is encased in a structured try/catch block returning uniform JSON response envelopes with HTTP status codes and { success: false, error: message } payloads. Unhandled promise rejections are caught gracefully. In a production pipeline, this is augmented with centralized Express error-handling middleware ((err, req, res, next) => {...}) and structured logging (Winston/Pino) connected to Datadog or Sentry for alerting."
Q19: How does the profile update endpoint securely handle password modifications?
"The /update-profile route enforces a two-step cryptographic check: if a newPassword is submitted, the user must also supply their currentPassword. The server compares the current password against the stored database hash with bcrypt.compare(). Only upon cryptographic match is the new password hashed with bcrypt.hash(newPassword, 10) and persisted. This prevents session hijacking exploiters from locking out legitimate users."
Q20: What metrics and monitoring would you implement in production?
"I would track the Four Golden Signals (Google SRE Framework):
1. Latency: p95 and p99 response times on search and booking endpoints.
2. Traffic: Requests per second (RPS) broken down by route.
3. Errors: 4xx (client errors/failed auth) and 5xx (database connection failures/server crashes) error rates.
4. Saturation: CPU/Memory utilization on Render nodes, MongoDB Atlas connection pool utilization, and IOPS."
